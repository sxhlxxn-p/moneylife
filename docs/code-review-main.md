# 코드 구조 검토 · 2026-11-22

검토 기준: GitHub main `9e5a63871ad1f8a0b824cce4a72e3435c852ae06`. 원격 main과 로컬 기준 커밋이 같은 것을 확인했다. 이번 이벤트·세션·운영 수정 전 코드를 대상으로 한다. 운영 소스 54개 파일을 크기·표현·의존성 관점에서 일괄 점검하고, 아래 주요 파일과 관련 테스트·문서를 상세 확인했다. 모든 경로의 동작을 수동으로 실행한 검토는 아니다.

현재 적용한 프론트 정리와 검증 범위는 [프론트 구조](frontend-structure.md)에 정리한다. 아래 파일 크기와 코드는 검토 기준 커밋의 기록이다.

## 판단

전체를 재작성할 정도로 복잡한 상태는 아니다. 금융 계산은 Engine에 분리돼 있고 서버도 기능별로 나뉘어 있다. 부담이 큰 부분은 프론트의 공유 전역 상태, 동적 화면 생성과 API 요청의 결합, 축약 CSS, 기능을 덧붙이며 오래된 설명이 남은 문서다. 파일 수 자체를 줄이거나 검증을 삭제하는 방향은 권장하지 않는다.

코드 문체만으로 작성 도구를 판별할 수 없다. 운영 소스에서 특정 생성 도구 이름·자동 작성 서명은 발견하지 않았다. 다만 반복 저자 머리말, 실제 동작과 어긋난 주석, 기능 추가 순서대로 길어진 README는 정리할 수 있다. AI 기능에 필요한 LLM·모델·검증 설명은 서비스 구현 내용이므로 삭제 대상이 아니다.

## 우선 수정할 구조

### 1. Client/src/app.js · 952줄

초기 조건·시간·저축·변경 기록 등이 전역 변수로 있고 server-plans.js, ai-client.js, paper-client.js가 이를 직접 참조한다. 재무 입력, 마을, 목표, 리포트, 이벤트, 모달, 로컬 저장, 버튼 연결까지 한 파일에서 처리한다. mlFinance는 start에서 파생한 복사 상태이며 saving/baseSaving 등 값의 역할도 처음 읽는 사람에게 명확하지 않다. worldtitle→ml-world-title 별칭과 mlEl/$, mlSimulation/simulate는 통합 과정의 호환 흔적이다.

권장 순서: 모달·금액/날짜 포맷 도구 분리 → 현재 상태의 읽기/변경 함수를 한 모듈로 모으기 → 재무 입력·대시보드·이벤트 화면 분리. 화면 코드가 임의로 전역 값을 쓰는 대신 이벤트 적용/계획 복원 같은 명시적 함수로 변경한다. 프레임워크 전환과 계산 변경을 동시에 하지 않는다. persist의 빈 catch는 저장 실패를 숨기므로 저장 불가 상태를 사용자에게 알리는 방향으로 개선한다. 브라우저의 만 원 단위와 서버의 원 단위 변환은 plan-state 경계에 유지하고 화면마다 변환 코드를 새로 만들지 않는다.

완료 기준: 동일 로컬 저장을 복원할 수 있고, 실행 중 조건 변경·서버의 늦은 응답·이벤트 선택에 기존 브라우저 테스트가 통과한다.

### 2. Client/src/styles.css · 316줄, 약 49.5KB

두 번째 줄 하나가 11,356자다. 이후 .ml- 계열 새 화면 스타일과 기존 화면/모달 스타일이 함께 있어 선택자 충돌과 사용 여부를 확인하기 어렵다. 줄 수가 적어 보여도 읽기 쉬운 CSS는 아니다.

먼저 포맷만 변경한 별도 작업을 한다. 그다음 공통 토큰/기본 요소/레이아웃/대시보드/모의투자/모달로 분리한다. 오래된 선택자는 DOM 생성 문자열과 prototype 사용 여부까지 확인한 뒤 제거한다. 단순히 index.html에 없다는 이유로 지우면 동적 모달이 깨질 수 있다.

### 3. Client/src/paper-client.js · 609줄

render, 설명, 주문 확인, 사본 비교, 생활 조건 변경, 요청 재전송, 저장 목록이 하나의 클로저에 들어 있다. compareSavedPlans와 editConditions 안에 여러 중첩 함수가 있어 API·임시 선택 상태·DOM 생명주기가 얽힌다. 요청 유실 후 복구 기능은 필요한 기능이며 길다는 이유로 없애면 안 된다.

먼저 pending 명령의 저장/재시도를 별도 모듈로 분리한다. 다음으로 주문 확인·조건 편집·비교 화면을 나눈다. 현재처럼 결과와 예약을 구분하는 계약과 중복 방지는 유지한다. “three allowed commands”라는 주석은 실제 다섯 명령 목록과 맞지 않는다.

### 4. Client/src/server-plans.js · 247줄

범용 API 요청, 기능별 오류 문구, 여정 저장/복원, 목록, 비교가 같이 있다. apiRequest의 오류 문구를 각 기능의 오류 사전으로 분리하고 HTTP·시간 초과 처리만 공통으로 둔다. 저장/계산이 두 요청인 경우 어느 단계가 완료됐는지 유지해야 한다. 이번 이벤트 저장은 별도의 원자적 API로 보완했다.

### 5. Client/index.html · 943줄

사이드바·대시보드·재무 입력·목표·설정·리포트가 정적 HTML 한 파일에 있다. 정적 페이지 구조 자체가 오류는 아니다. 다만 inline onclick 문자열과 script 로드 순서에 대한 의존은 테스트와 변경을 어렵게 한다. 화면 단위 템플릿이나 ES 모듈로 나누는 편이 좋다. React는 현재 설치되어 있지 않다. 이 정리를 위해 곧바로 전체 React 이전을 시작할 필요는 없다.

## 서버에서 정리할 부분

- paper.py 271줄: 저장·중복 요청 확인·API 핸들러가 섞여 있다. save/existing/owned_paper와 응답 조립을 서비스 계층으로 옮기고 핸들러는 요청 검증·호출·응답에 집중시킨다. 여러 기능을 포괄하는 범용 CRUD 프레임워크를 새로 만드는 것은 과하다.
- ai.py 172줄: 조건 추출·재질문·승인 적용·설명 캐시를 분리할 수 있다. 기존 build_candidate와 설명 검증 모듈은 재사용한다. 새 모델 래퍼를 중복으로 만들 필요는 없다.
- investment_engine.py validate_result 71줄: 길지만 자산 합계·가격 기준·주문 체결을 검증하는 서로 다른 불변식이 있다. 검증을 삭제하지 말고 경로/평가/체결 검증 함수로 나눈다. 검증 책임은 엔진과 서버 경계에 각각 남겨 둔다.
- paper_schemas.py 301줄: 요청·응답 계약이 모인 파일이다. 길다는 이유만으로 우선 분리할 필요는 낮다. 기능 확장 시 order/plan/comparison 모델별 분리를 고려한다.
- ai_evaluation.py: 평가용 코드가 app 아래에 있지만 운영 fallback이 아니다. 테스트·평가 도구를 정리할 때 Test/ai 쪽으로 이동하고 해당 import를 함께 바꾼다.

## 주석과 문서

저자 이름 머리말은 기능 설명에 기여하지 않으면 줄이고 저자 정보는 Git 기록으로 관리한다. 상식적인 동작을 다시 적는 주석보다 금액 단위·반올림·체결 시점·중복 요청처럼 이유를 알아야 하는 규칙을 남긴다. 중요한 출처와 팀원의 원본 작업 기록은 보존한다.

README의 현황 문단에는 “모의투자 화면/서버 연결 미구현”이라는 오래된 설명이 있었고, 서버 README에는 뒤에서 구현을 설명한 주문 취소를 앞에서는 후속 작업으로 적고 있었다. 이번 변경에서 해당 설명과 이벤트 저장 안내를 수정했다. 이후 README는 실행 방법·현재 기능·남은 작업을 짧게 유지하고 상세 계약은 Shared와 docs로 연결한다.

## 정리 순서

1. 기능 변경 없이 CSS·짧은 변수명·어긋난 주석을 정리한다.
2. API 요청과 오류 처리를 화면 코드에서 분리한다.
3. 전역 게임 상태를 명시적인 상태 API로 감싼다.
4. 대시보드/재무 입력/이벤트 및 모의투자 하위 화면을 분리한다.
5. 서버의 저장 서비스와 검증 함수를 분리한다.

각 단계는 별도 변경으로 검토하고 기존 계산/저장/재시도/소유권/브라우저 테스트를 통과시킨다. 폴더 수를 늘리는 것 자체를 목표로 삼지 않는다. 프론트 상태·화면·HTTP·투자 명령·CSS 분리는 frontend-structure.md의 범위로 적용했다. 서버 저장 서비스와 검증 함수의 추가 분리는 후속 작업이다.
